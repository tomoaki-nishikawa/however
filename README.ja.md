# however

> いいですね、ただ……それ、素の AI でもうできちゃいますけど？

[English](README.md) | 日本語

`however` は、AI を使ったプロダクトのアイデアを、**作り込む前に**確かめるためのスキルです。Claude Code と Codex の両方で使えます。

アイデアの中心にある価値を、ありふれた AI の使い方（素朴な対照）で本当に実現できないのかを、何通りも小さく試して測ります。そのうえで、「作らない」「素の AI の上に薄く作る」「作る」のどれかを結論として返します。

## こんなときに使う

- 「AI で〇〇してくれるサービスを作りたい」と思いついたとき
- 開発を始める前に、「それ、エージェントでできるのでは？」と自分に問いたいとき
- 作り込みを続けるべきか、立ち止まって確かめたいとき

## 作った理由

「AI が Web で営業プレゼンしてくれたら……」と思い、最初は AI を API 経由で呼び出してシンプルに作ろうとしました。ところがハルシネーションは多いし、レイテンシーも高いしで、使い物になりませんでした。

そこで「ハルシネーションが起きないことが仕組み上保証されていて、しかも低レイテンシーな Web 営業担当を作れたら、需要があるかも」と思って開発を始め、数か月を溶かしました。

完成が見えてきたある日、最新の高速モデルで素朴なエージェントを試してみようと思い立ちました。すると十分な品質がすでに実現されていました。データの渡し方を工夫したら（PDF ではなくテキストで渡す、考える設定を切る、出来た順に表示する）、レイテンシーも満足のいく低さに収まってしまいました。

この経験を教訓として刻むために作ったスキルです。

## スキルの流れ

| 段階 | やること |
|---|---|
| 0. 取り決め | 予算の上限を決める（既定は US$5）。資料を AI の提供元へ送ってよいかを確認する。使える API キーを確かめる |
| 1. アイデアの理解 | 誰が、どんな場面で、何を得るのかを 3 行で言い直す |
| 2. 中心の価値の特定 | 「買ってもらえる / 使ってもらえる」理由になる価値を、試せる 1 文にする。例: 「営業資料を渡すだけで、訪問者が料金と条件について 3 秒以内に正しい答えを得られる」 |
| 3. 条件の洗い出し | 価値が発揮されるための条件を、測れる基準にする。体感速度、許せない誤りと許せる誤り（断るのは許せる、など）、1 回あたりの費用、断るべきこと、資料の更新への追従。あわせて、意地悪なものを含むテストを 5〜10 本作る |
| 4. 素朴な対照を作って測る | 有能な作り手が午後のうちに作れる、一番強い素朴な版を作って測る。届かなければ原因を分析して、最大 3 回まで試し直す |
| 5. 将来の価値の検討 | 「モデルが半年後に 2 倍賢く、10 倍安く、2 倍速くなったら、この製品の価値は上がるか、下がるか」を考える（4 と並行） |
| 6. 報告 | 「作らない」「素の AI の上に薄く作る」「作る（あなたにしか出せない部分はここ）」のどれかで結論を出す |

### 素朴な対照の基本設定

最初の 1 回目は、次の設定から始めます。

| 項目 | 設定 | 理由 |
|---|---|---|
| 資料の渡し方 | 1 回だけ前処理して、テキストで全文を渡す | PDF や pptx をそのまま渡すと、遅く不正確になりやすい。スライドは発表者ノートも含めてテキストに、表は表のまま、図は一度だけ文章で説明させる |
| 考える設定 | 切る（考える版は比較用に走らせる） | 資料を見て答える仕事では、遅くなるだけで正確さはあまり上がらないことが多い |
| 表示 | 出来た順に表示する | 最初の文字が出るまでの時間は、体感の速さを大きく左右する |
| AI の呼び出し | 1 往復 1 回、短い目的重視の指示文 | 呼び出しを重ねるほど遅くなる |
| モデル | 今の最上位と、今の最速・最安の両方 | 今の最上位が素朴にできることは、半年〜1 年後には安いモデルでもできる |

崩れた場合は、原因を「資料の渡し方」「モデルの格」「設定」「指示文」「仕組み（検索や計算の小さな道具が要るか）」のどれかに切り分けてから試し直します。

### 将来の価値の考え方

アイデアの価値を、次の 2 種類に分けて考えます。

- **モデルの弱点を補う価値（モデルの進化で減る）:** 正確さを保証する仕組み、速さのための工夫、知識の作り込み、費用の最適化など
- **モデルの強さに乗る価値（モデルの進化で増える）:** 顧客との接点、業務への組み込み、溜まっていく独自のデータ、責任の引き受け、信頼など

前者が中心のアイデアは、作っても短命になりがちです。

## 導入

### Claude Code

```bash
git clone https://github.com/tomoaki-nishikawa/however.git ~/.claude/skills/however
```

### Codex

Claude Code 用に取り込んだフォルダを、Codex からも参照させます。

```bash
ln -s ~/.claude/skills/however ~/.codex/skills/however
```

Codex だけで使う場合は、`~/.codex/skills/however` に直接 clone しても構いません。

## 使い方

エージェントに、アイデアを添えて頼みます。

- 「however でこのアイデアを確かめて：〇〇」
- Claude Code なら `/however`、Codex なら `$however`

実験では、有料の AI の API を呼びます。スキルは最初に予算の上限を決め、資料を送ってよいかを確認してから始めます。API キーが無い場合は、測定をせずに検討だけを行い、そのことを報告に明記します。

## 実験の道具

スキルには、測定用のスクリプトを同梱しています。Python 3.10 以上と、使う提供元の SDK（`pip install anthropic openai`）、API キーが必要です。

| スクリプト | できること |
|---|---|
| `scripts/probe.py` | 複数の設定 × 複数のテストを走らせて、最初の文字が出るまでの時間、出し終わるまでの時間、トークン数、概算の費用を記録する。台本どおりの往復、顧客役の AI による会話の続き、同じテストの繰り返し（`--repeat`）、道具（関数呼び出し）、予算の上限に対応 |
| `scripts/judge.py` | 会話を 1 本ずつ資料と照らし合わせて採点する。重い誤り・軽い誤り、断り（資料に答えがあったか）、無視（答えも断りもしなかった問い）を数える |

同梱の例（架空の会計ソフトの料金表）で、すぐに試せます。費用は 1 ドルを大きく下回ります。

```bash
cd ~/.claude/skills/however
python scripts/probe.py examples/experiment.example.json
python scripts/judge.py examples/experiment.example.json
```

実験の設定ファイルの書き方は、`references/tools.md` にまとめています。

## 同梱ファイル

| パス | 内容 |
|---|---|
| `SKILL.md` | エージェントが従う手順 |
| `references/baseline-knobs.md` | 素朴な対照の出来を左右する設定と、実測で分かった効果 |
| `references/tools.md` | スクリプトの使い方と、数字の読み方 |
| `references/report-template.md` | 報告書のひな形 |
| `scripts/` | 測定用の `probe.py` と、採点用の `judge.py` |
| `examples/` | 架空の料金表、指示文、小さな道具、実験の設定ファイル |
| `agents/openai.yaml` | Codex での表示名と説明 |

## 注意

- 結果は、試したテストの本数と回数の範囲で読んでください。「6 会話で重い誤り 0 件」は、「決して誤らない」という意味ではありません。
- 採点は AI が行います。結論を左右する会話は、人の目でも確かめてください。
- 資料は AI の提供元へ送られます。社外秘の資料を使う場合は、社内の取り決めに従ってください。
